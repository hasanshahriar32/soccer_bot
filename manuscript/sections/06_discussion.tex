\section{Discussion and Application Development}
The architecture broadens the task from following a detected ball to coordinating object retrieval. Its useful abstraction is the evidence at a subsystem boundary: vision proposes an authorized target, navigation establishes a pickup region, the base confirms rest, the arm establishes a grip, and placement confirms release. The mission model exposes these obligations even where the present hardware interface lacks the necessary feedback. A nominal Boolean trace therefore demonstrates logical progress under its assumptions, while the command analysis identifies what the concrete gateway can actually express.

The next application step is to instantiate these observations with measured quantities. This requires a task-specific visual dataset and held-out recognition results; calibrated camera--LiDAR--arm frames and contact geometry; feedback for base rest, grip, and release; and timed physical runs covering navigation, pickup, transport, and deposit. Sensor-age limits must follow measured acquisition and transport behavior. Force, payload, containment, and environmental compatibility must be evaluated for the designated object class. A general RGB category detector cannot establish an unknown material's hazardous properties.

The present evidence consists of a discrete reference model, isolated source execution, and ideal geometry. It establishes neither physical obstacle-avoidance performance nor deployment suitability in hazardous environments. Ball-based surrogates let the retrieval interfaces be studied without exposing participants to hazardous material; transfer to a specific application remains an explicit validation step. Compared with application-tested platforms~\cite{bird2022vega,kemp2022stretch}, HazBot's contribution is this transparent embedded integration and reproducible characterization path.
